# 庄园地下城功能实施规划

> 本文描述旧自动战斗版本及其兼容规则。新动作刷宝 Beta 的产品边界与分工见[开发指南 V0.2](dungeon-beta-development-guide.md)，技术调整见[架构重构方案](dungeon-beta-architecture.md)。新版本采用游戏厅平级入口、共享金币与玩家装备交易，不能把本文旧流程直接套用到新模式。

修订日期：2026-09-23

依据：地下城战斗系统策划案 V1.1，2026-09-23 修订版

状态：开发规格。`dev/dungeon-core` 分支已完成 M0～M3：版本化目录、属性与战斗内核、装备存档、服务端起局、暂停/恢复/倍速、按服务器时间补算、胜负结算、奖励事务、待领取和断线查询。现有联调目录只有一个普通遭遇及一套固定奖励；M4 的可玩界面与 M5 的完整内容仍待实施。下文的模块清单保留为目标结构，具体进度以本段和代码为准。

先交付可保存、可恢复、可验收的单人自动战斗闭环，再增加构筑。v0.1 只实现六项属性、单敌人普通攻击、暴击、简化首领阶段、基础装备和胜利结算；v0.1.1 补齐累计五次通关扫荡；v0.2 分批实现技能、状态、随机词缀与打造。本规划面向程序、界面和数值配置开发，按模块输入输出、事务边界和验收用例安排工作。

参考文档中的建议值作为联调初值，不能直接视为线上经济参数。本次不引入独立战斗等级、职业、多人副本或 PVP；涉及经验时不默认增加庄园经验。所有角色、首领、日志、资源键和配置示例使用通用名称。

## 1 版本边界与旧稿调整

### 1.1 首版范围

| 能力 | v0.1 必须交付 | 后续交付 |
| --- | --- | --- |
| 战斗单位 | 一个玩家对一个敌人，每次挑战一个遭遇 | v0.2 按内容需要增加一对多 |
| 玩家属性 | HP、ATK、DEF、CRIT、CRIT_DMG、SPEED | 技能阶段再评估 MP、法强、抗性和穿透 |
| 攻击 | 单体普通攻击、独立暴击、固定种子波动 | 技能、冷却、资源与自动释放优先级 |
| 装备 | 六部位，各一件；普通、优秀、稀有、史诗；固定模板属性 | 随机词缀、底材、打造材料、装备联动 |
| 首领 | 血量阈值、相对基础值的属性变化、一次性追加普攻 | 专属技能和状态机制 |
| 关卡 | 顺序解锁的普通、精英、首领遭遇 | 路线、营地、商店、多节点探索 |
| 操作 | 开始、暂停、恢复、x1、x2、离开页面、放弃挑战 | 战前技能优先级、局内选择 |
| 持久化 | 装备、挑战快照、事件、结果、奖励、通关次数 | 扫荡任务、局内构筑、材料 |
| 扫荡 | 保存有效通关计数，界面不提供未实现按钮 | v0.1.1 达到五次后开放 |
| 状态与环境 | 仅首领阶段修正，无通用状态引擎 | v0.2 状态先行，天气与肉鸽后置 |

六部位固定为 `weapon / helmet / chest / belt / boots / accessory`。武器只有一个槽；史诗在 v0.1 也只是固定属性模板，不提前承诺特殊机制。外显名称保持不变，装备品质不能绕过伤害公式。

### 1.2 明确替换旧稿的规则

| 旧稿规则 | 本版实施决定 |
| --- | --- |
| 八项主要属性、物理与法术两条路径 | v0.1 统一 ATK 对 DEF，法术路径后置，不保留隐藏法术计算 |
| 攻速按每秒攻击次数显示，首击等待完整间隔 | 改用 SPEED 数值，100 对应 2 秒间隔，首击等待半个间隔 |
| 无伤害波动，最低伤害 0，多增伤与等级乘区 | 波动 0.95～1.05，最终最低 1，无等级压制和额外增伤乘区 |
| 玩家行动固定排在怪物之前 | 同时间先比较有效 SPEED，再按稳定 actor_id 排序 |
| 一局 8～12 节点，生命跨房间继承 | 一次挑战一个敌人，每次从满生命开始 |
| 单场统一 180 秒超时 | 普通及精英 60 秒，首领 180 秒 |
| 随机词缀、打造、环境和六槽肉鸽都在首版 | 分批进入 v0.2，不作为基础战斗上线依赖 |
| 失败保留已完成节点收益 | v0.1 没有多节点累计奖励，失败、超时、放弃均无本次奖励 |
| 同一地下城加难度统计完整探索通关 | v0.1 以 `challenge_id + difficulty_id` 计数；将来多节点关卡使用新 ID |

这些是实现规则的替换，不得同时保留两套公式供不同界面使用。旧稿的复杂玩法移入第 12 节，不以“预留接口”为由先做空系统。

### 1.3 对参考文档未定项的落地选择

- 采用服务端权威结算，浏览器不提交伤害、胜负、奖励或随机种子。
- 每个遭遇满生命开场，失败无参与奖励，不扣已有金币和装备。
- 不开放正式跳过战斗或客户端立即结算；开发模拟工具可以直接计算完整结果。
- 暂停是账号级战斗暂停，同时停止服务端模拟时间与事件播放；断线本身不暂停，重连补算当前遭遇，不自动开始下一场。
- 首版不发经验，不把战斗次数换算为人物属性。参考文档的经验奖励字段暂不进入协议。
- 通用首领称为“遗迹守卫”，内部 ID 使用 `ruins_guardian`；新内容统一使用无人物指代的名称。

项目现有后端为 Python、SQLite 和 WebSocket，前端为原生 JavaScript 模块。地下城继续使用现有账号、金币与连接设施，不新建 HTTP 服务，不接入多人房间匹配。

## 3 v0.1 数值与配置合同

### 3.1 属性表示

服务端和协议使用统一单位；百分比避免浮点歧义。下表是存储单位，不直接作为界面文案。

| 字段 | 存储与校验 | 界面 |
| --- | --- | --- |
| `max_hp`、`hp` | 正整数上限；当前值 0～max_hp | 当前生命 / 最大生命 |
| `atk`、`defense` | 非负整数 | 攻击力、防御力 |
| `crit_bp` | 0～10000 基点；100 基点为 1 个百分点 | 暴击率百分比 |
| `crit_damage_bp` | 至少 10000，默认 15000 | 暴击伤害 150% |
| `speed` | 最终值限制 25～500；配置中的非正数直接拒绝 | 攻速 100，详情显示间隔 2.00 秒 |

属性配置必须是有限数字，拒绝布尔、NaN、Infinity 和未声明字段；模板整数不能接受小数字符串。生命、攻击、防御各设配置安全上限，原型统一 `1_000_000`，暴击倍率上限 `100000`，改上限必须重跑溢出和事件容量测试。CRIT 汇总后截断到 0～10000；内容配置建议不高于 6000。负防御属于错误，不通过分母修正容错。

解析顺序为角色基础值 → 装备固定加值 → 首领阶段修正 → 各字段上限。v0.1 没有随机词缀或玩家临时状态步骤。战力若展示，只作比较，不参与任何计算或关卡门槛。

### 3.2 时间与随机数

```text
完整攻击间隔 = clamp(2 × 100 / SPEED, 0.4, 5.0) 秒
interval_us = round_half_up(完整攻击间隔 × 1_000_000)
first_action_us = round_half_up(interval_us / 2)
next_action_us = 本次行动时间 + 按本次行动结束时有效 SPEED 计算的 interval_us
```

`clamp(value, min, max)` 的参数顺序固定如上。使用整数微秒排期，中间除法用整数有理数和明确的四舍五入函数，避免 Python 默认偶数舍入与客户端算法不同。精英采用普通战超时；`next_action_us >= timeout_us` 时先判超时，不执行恰好踩线的攻击。

首版不需要随机闪避。每次有效攻击固定消耗两个抽样值，顺序为伤害波动、暴击，即使暴击率为 0 或 100% 也消耗第二个值。失效行动不消耗随机数，首领追加攻击遵守同样规则。

为方便重启与版本复现，新增项目内确定性抽样器：种子使用服务端产生的 32 字节随机值；第 n 次抽样为 `SHA256(seed_bytes || uint64_be(n))` 的无符号大端整数，对目标区间大小取余。首版接受这一固定映射的极小分布偏差，不在不同模块改用语言默认 random。波动抽取整数 `[9500,10500]`，暴击抽取 `[0,9999]`，后者小于 `crit_bp` 时暴击。检查点保存计数器；`rng_version=1` 固定编码与算法。

战斗种子和掉落种子分别生成与保存，互不消耗对方的抽样序列。种子只供服务端测试与排障使用，不出现在进行中战斗的公开响应中。

### 3.3 伤害唯一公式

```text
variance_bp = 9500～10500
critical_bp = 暴击时 crit_damage_bp，否则 10000
attack_scale_bp = 普攻 10000，首领阶段追加攻击 15000

raw_damage = atk × 100 / (100 + target_defense)
             × variance_bp / 10000
             × critical_bp / 10000
             × attack_scale_bp / 10000
damage = max(1, floor(raw_damage))
hp_loss = min(target_hp, damage)
target_hp = target_hp - hp_loss
```

所有乘数合并成整数分子与分母，仅最后做一次整除；`damage` 超出 JavaScript 安全整数范围时返回 `numeric_overflow`，不把异常数发给浏览器。ATK 为 0 也造成最低 1 点伤害，这是本版明确规则。没有护盾、等级差、抗性、法穿或增伤乘区。

`damage` 是计算伤害，`hp_loss` 是实际扣血。事件同时保存两者；日志和总伤害统计使用 `hp_loss`，击杀超额伤害不重复累计。例：ATK 120、DEF 50、波动 10000、不暴击得到 80；默认暴击得到 120。若目标仅剩 35 HP，记录 damage=120、hp_loss=35、hp_after=0。

```json
    "display_name": "遗迹软泥",

```

启动时校验目录：装备与敌人的 ID 唯一，挑战以 `(challenge_id, difficulty_id)` 判重；装备部位、引用、正权重、前置无环、阶段阈值、持续时间及 `visual_id` 格式均需合法。字符串前置指同难度关卡；跨难度前置写成 `{ "challenge_id": "...", "difficulty_id": "..." }`。资源文件存在性由素材交付检查负责。配置错误阻止新挑战；已保存挑战使用自己的完整配置快照。

## 4 模拟状态机与首领阶段

### 4.1 战斗内核

```text
INIT → READY → FIGHTING → ENDING → RESOLVED
  └── ERROR      └──────── ERROR
```

READY 初始化满生命并发出 BattleStarted；进入 FIGHTING 不等待浏览器入场动画。ENDING 立即锁定结果、取消队列并发出 BattleEnded，随后生成结果进入 RESOLVED。参考文档中准备和结束动画的等待仅保留在表现层，服务端不以动画回调作为状态推进条件。

模拟循环必须按以下顺序执行：

1. 检查结果是否已锁定；锁定后不再处理行动或阶段。
2. 取最早行动时间与 timeout_us 的较小值作为下一处理时点。若超过本次 target_time_us，保存检查点；否则若为超时边界，立即锁定 timeout。即使下一次攻击排在超时之后，也必须在超时处结束。
3. 在该时间戳的有效行动中，按当前有效 SPEED 降序、actor_id 字典升序选择一个。玩家 ID 固定 `player:0`，敌人固定 `enemy:0`，完全同速时敌人先行动，不使用账号名称或创建顺序。
4. 再次检查双方存活，生成 AttackStarted，抽取波动与暴击，计算并应用扣血，生成 DamageApplied。
5. HP 为 0 时立即发 ActorDied 并锁定胜负，取消死者后续行动。本版没有反伤或持续伤害，不存在同时死亡分支。
6. 目标为仍存活的首领时，处理本次跨过的阶段，再处理阶段追加攻击；追加攻击致死也立即结束。
7. 若战斗继续，为刚完成的常规行动排下一次攻击；重新选取同时间戳尚未执行的行动，不沿用已过时的速度排序。

检查点至少保存 `sim_time_us`、双方 HP、当前阶段、已触发阶段 ID、每个单位的 next_action_us、RNG 计数器、事件序号、累计 hp_loss 和终止状态。未终止时 sim_time_us 推进至本次 target_time_us，即使期间没有攻击；终止时停在实际结束时间。纯函数不得修改传入快照，不能使用系统时间作为随机或排序输入。

### 4.2 首领初始阶段表

| 阶段 ID | 条件 | 相对快照基础值的属性 | 一次性事件 |
| --- | --- | --- | --- |
| `phase_1` | 开场 | ATK 100%，SPEED 100% | 首领血条出现 |
| `phase_2` | HP ≤ 最大 HP 的 50% | ATK 115%，SPEED 110% | 阶段提示 |
| `phase_3` | HP ≤ 最大 HP 的 20% | ATK 130%，SPEED 120% | 阶段提示，并执行一次 150% 标准攻击 |

判断阈值使用整数交叉相乘。属性从初始快照重算，ATK、SPEED 修正后向下取整并应用上限；阶段三不是在阶段二基础上再乘 1.30。阈值只触发一次，阶段 ID 集合随检查点落盘。

一次伤害从 60% 打到 10% 时，按 50%、20% 顺序生成阶段事件，最终保留阶段三；一次伤害直接击杀时先结束战斗，不触发临死阶段。表现可合并跨阶段转场，结构化事件不能丢失。

首领速度变化不重排已经预约的常规攻击；下一次常规攻击结束后使用新速度排期。阶段追加攻击立即插入当前伤害后的同一时间戳，排在下一名常规行动者之前；它使用阶段三有效 ATK、独立波动和暴击，不重置常规攻击时钟，也不递归触发新的追加攻击。事件标记 `action_kind=phase_extra`。

## 5 暂停 倍速 离线与恢复

### 5.1 业务状态与时间

挑战持久化状态为 `running / paused / settled / abandoned / error`，与内核临时状态分开。结果 outcome 为 `victory / defeat / timeout / error / abandoned`；后者是主动退出的业务结果，不进入伤害计算。

采用请求驱动补算，避免为每个账号维护逐帧任务。保存 `sim_anchor_us`、`wall_anchor_ms`、`playback_rate` 和 checkpoint；运行时由服务器时钟计算：

```text
target_time_us = min(timeout_us, max(checkpoint.sim_time_us,
  sim_anchor_us + max(0, server_now_ms - wall_anchor_ms) × 1000 × playback_rate))
```

`playback_rate` 只允许 1 或 2，改变现实时间映射，不修改动作间隔、波动抽样或模拟事件顺序。暂停时目标时间固定。服务端时钟注入以便测试；机器时钟回拨不得倒退模拟进度，前跳最多补算到单场超时。部署保证时钟同步。

客户端在战斗页每 500 毫秒请求一次同步，后台页可降频；关页或断线后不再同步，回来时按持久化锚点补算。没有请求时无需持续执行 CPU 模拟。离线不会自动进入下一场，暂停状态重启后仍暂停。

暂停、变速、放弃都先按旧锚点补算到服务器收到命令的时间。若此前已经结束，优先完成结算并返回终态；否则提交新状态或新时间锚点。恢复把墙钟锚点设为当前服务器时间，不补算暂停区间。该规则避免在已胜利后用放弃撤销结果，也避免跨设备把时间拨回。

### 5.2 避免长事务和并发覆盖

同步分成读、计算、提交三步：

1. 短读事务取挑战和 revision；关闭连接后按冻结配置运行纯模拟。
2. 打开写事务，执行 `BEGIN IMMEDIATE`，重新核对账号、状态与 revision。
3. 若 revision 未变，将新检查点、事件、终态和可能的奖励一并提交；改变时增加 revision。若已变，丢弃本次计算，重新读取，最多重试两次，仍冲突返回 `state_conflict`。

所有写事务内无 await、无动画等待、无整场模拟。事件序号由检查点决定，通过 `(battle_id, sequence_id)` 唯一约束防止并发重复追加。重复同步在目标时间没有推进时不增加 revision。

起局在单一短事务中建立只读快照、初始检查点、账号活动记录和请求回执。后续故障从该快照恢复，不重新挑敌人、抽种子或读取当前装备。数据库写失败时回滚整个推进，保留旧检查点，下次得到同一结果。

正常败北或超时写入 settled 和对应 outcome；主动放弃写 abandoned；可确定的模拟错误写 error，保存诊断，三者均在提交终态时释放活动记录且不发奖。存储失败或版本不兼容不冒充模拟错误、不释放尚未处理的活动记录。起局前配置校验失败则不创建挑战。

### 5.3 客户端事件消费

每个事件包含 `battle_id / sequence_id / battle_time_us / event_type / source / target / value`，必要时携带 `hp_after / damage / hp_loss / is_critical / phase_id / action_kind`。source、target 可以为空，但字段类型固定。

| 事件 | 表现要求 |
| --- | --- |
| `BattleStarted` | 初始化双方血条和敌人名称 |
| `AttackStarted` | 普攻动作或简化位移 |
| `DamageApplied` | 按 hp_after 更新血条，显示实际扣血；暴击同时有文字或形状提示 |
| `BossPhaseChanged` | 显示阶段、有效属性变化，支持合并同次跨阶段的动画 |
| `ActorDied` | 停止该单位动作，播放死亡反馈 |
| `BattleEnded` | 停止队列，转入结算或失败信息 |

暴击标记并入 DamageApplied，避免独立暴击事件与伤害事件关联错位。前端维护最大已应用 sequence_id，重复包跳过，缺号按游标补取。每页最多 200 事件且 JSON 不超过 128 KiB，返回 `next_cursor / has_more`；服务端完整保存事件，UI 只保留最近 100 条文本日志。

断线重连以最新权威检查点重建血条，将消费游标设为该检查点对应序号；历史分页仅用于日志，不重新播放旧伤害。普通增量包不能用最终 HP 先覆盖尚待播放的伤害过程。结束快照始终能够直接重建结果，不依赖任何非关键动画回调。

## 6 装备 关卡与奖励闭环

### 6.1 装备最小实现

装备实例字段为 `item_id / owner / template_id / slot / quality / stats_json / sell_coins / locked / location / version / created_at`。`stats_json` 是生成时固化的固定属性，不从日后修改的模板重新推导；`location` 为 `bag / pending / sold`。出售后保留已消耗记录以便幂等，不再次参与容量和穿戴。

装备、卸下、锁定、对比、单件出售进入首版。每个槽位仅引用本人 bag 中的未出售装备；穿戴引用保持唯一。运行或暂停中的挑战禁止换装和出售其快照引用装备；其他未锁定备用装备可以出售。已装备和已锁定物品禁止出售，批量出售与分解后置。

新手初始化只发一次六件普通装备并自动穿戴，使用资料字段 `starter_granted` 与装备入库同事务。联调基底为 HP 200、ATK 0、DEF 0、CRIT 5%、CRIT_DMG 150%、SPEED 100；武器 ATK +30，头盔 HP +20，胸甲 DEF +12，腰带 HP +50，鞋子 DEF +8，饰品 HP +30，合计 HP 300、ATK 30、DEF 20。此套装配合第 3 节普通敌人形成首个可复现闭环。

第一次 get_dungeon 在短事务内幂等初始化资料、新手装备和首个关卡解锁；再次读取不重复赠送。初始化后只读取状态，不因此推进当前战斗。并发首次进入也必须只产生六件新手装备。

初始装备容量 60，材料系统尚未开放。装备对比调用同一 StatsResolver，显示替换后六项属性与攻速间隔；v0.1 不显示词缀空位、法强、联动或未实现的打造按钮。

### 6.2 关卡最小内容

首版一个区域、一档难度，配置 3 个普通遭遇、1 个精英、1 个首领。每个挑战 ID 固定对应一个敌人，首次胜利解锁配置中的后继挑战；同一已解锁挑战可重复进入。前置关系由配置表示，不以字符串大小判断。

关卡预览显示敌人六项属性、首领阶段、可能奖励和有效通关次数。生命不跨挑战继承，首版没有路线奖励、营地恢复或局内货币。

掉落最少提供每部位两种固定模板及四种品质的明确属性版本。不要给同一模板再隐式乘一次品质系数。普通、精英和首领分别配置奖励池；首领胜利保证至少一件稀有或史诗，史诗概率独立配置，不增加未定义的累计保底。

### 6.3 奖励提交

掉落包只在胜利后由服务端生成，保存 `reward_token`、金币数和完整装备实例。失败、超时、放弃、模拟错误均为零奖励；已拥有金币、装备和解锁进度不减少。重试按钮是一次新挑战，使用新 request_id；网络重发保持原 request_id。

`reward_token` 由账号与 battle_id 确定且唯一。一次写事务内完成：

1. 检查挑战所有权和 revision，确认之前没有结算。
2. 写入最终检查点、事件和 BattleResult。
3. 生成固定掉落包并插入唯一奖励凭据。
4. 调用 `adjust_coins(conn, username, delta, "dungeon_reward", detail, ref)`，ref 使用 `dungeon:<battle_id>`。
5. 写入装备；仓位不足的部分直接记为 pending，不丢弃、不自动出售。
6. 更新本挑战通关次数和首次解锁，状态改为 settled，释放账号活动记录；若由控制命令触发，同时写入该动作回执，然后提交。同步触发结算无需新增同步请求回执。

现有 `adjust_coins` 的 ref 不是唯一约束，不能只靠金币流水实现幂等。真正的防重由挑战终态、唯一 reward_token 和同事务检查共同保证。提交后再定向发送结果、金币余额和地下城版本更新；发送失败不撤回奖励，重连查询即可恢复。

数据库失败显示“结算保存失败，可重试”，不伪装成战斗失败，也不创建第二个奖励包。没有结算成功前不显示已到账；模拟得到胜利不等于奖励已经保存。

### 6.4 满包处理

背包满仍允许本场胜利和通关次数提交，金币正常到账，装备作为已持有的 pending 实例留存。领取只是同一实例从 pending 移到 bag，不重新抽取、不再次发金币。支持按剩余格数领取部分装备，领取请求原子校验目标实例和容量。

存在 pending 装备时禁止开始新挑战或扫荡，界面提供出售备用装备和领取入口。首版不做付费扩容或到期删除。暂定同时最多 20 个待领取实例，奖励配置校验单场最大发装数不超过 20；已有 pending 会阻止下一局，保证上界成立。

### 6.5 经济发布条件

联调奖励池使用测试环境配置，线上金币数、出售价格和概率表必须先完成模拟报告。报告至少列出普通/精英/首领在低、推荐、高配下的成功率、现实时间净金币、掉落装备与出售后的总收益、x2 与扫荡收益。

对照 [庄园经济基线](estate-economy.md) 时复查现行 `estate/catalog.py` 和实际规则，不能将旧文档的模拟收益当作当前保证收益。首版不设入场费、不新增每日硬上限；通过奖励与耗时配置控制长期产出，不通过客户端动画控制经济。

## 7 数据表与一致性约束

下表为 v0.1 最小持久化规格。账号沿用 `username TEXT COLLATE NOCASE`，不把昵称作为关联键；所有 JSON 均在写入前做 schema 校验。

| 表 | 关键字段 | 索引和约束 |
| --- | --- | --- |
| `dungeon_profiles` | username、starter_granted、bag_capacity、version | username 主键；容量正数；version 每次业务变更递增 |
| `dungeon_items` | 第 6.1 节实例字段；owner 对应 username；取得时冻结 display_name、visual_id | item_id 主键；索引 `(owner, location)`；品质、部位、位置枚举校验 |
| `dungeon_loadout` | username、slot、item_id | 主键 `(username, slot)`；item_id 唯一；服务层校验所属账号与槽位 |
| `dungeon_runs` | battle_id、username、challenge_id、difficulty_id、status、snapshot_json、snapshot_hash、checkpoint_json、result_json、reward_token、revision、sim_anchor_us、wall_anchor_ms、playback_rate、created_at、updated_at | battle_id 主键；索引 `(username, created_at)`；版本非负、速率枚举 |
| `dungeon_active_jobs` | username、job_kind、job_id | username 主键，确保挑战与扫荡共享一把账号级活动锁；job_id 唯一 |
| `dungeon_events` | battle_id、sequence_id、battle_time_us、event_json | 主键 `(battle_id, sequence_id)`；按游标读取 |
| `dungeon_rewards` | reward_token、username、battle_id、payload_json、created_at | reward_token 主键；battle_id 唯一；记录已提交奖励包 |
| `dungeon_progress` | username、challenge_id、difficulty_id、clear_count、unlocked、first_clear_at | 三字段联合主键；次数非负 |
| `dungeon_actions` | username、request_id、action_type、request_hash、result_json、created_at | 主键 `(username, request_id)`，拒绝同 ID 不同内容 |

request_id 由客户端生成，长度 1～96，限制为字母、数字、下划线与连字符。请求摘要包含类型和规范化业务参数，排除游标与传输时间。先查已完成回执，再检查 expected_version，保证响应丢失后的原请求可以返回原结果。同 request_id 不同动作或参数返回 `request_conflict`。

动作回执不代替奖励唯一约束；清理旧事件或回执也不得使同一 battle_id 再次发奖。v0.1 暂不清理奖励凭据和动作回执，压测评估数据增长后另定保留策略。调试种子和完整快照仅限维护入口读取。

建表采用 `CREATE TABLE IF NOT EXISTS`；新增字段先检查 PRAGMA。当前连接工厂没有启用 `PRAGMA foreign_keys`，不能仅写 REFERENCES 就假定级联生效：本模块使用显式所有权检查和事务内清理，并增加用户删除触发器清理地下城从属记录。触发器、动作与挑战查询均采用统一账号比较规则；清理行为必须有测试。

配置更新不重算已有装备、不改已发奖励。已开档账号读取状态时补齐新增关卡进度，并依据已通关前置更新解锁。进行中挑战绑定 simulation_version 和 reward_rng_version；部署必须保留活跃版本的模拟器与奖励抽取器，或先关闭新开局并等待旧局清空。遇到不支持的活跃版本时保持存档并返回 `unsupported_version`，禁止用新版本重算或悄悄清空。

## 8 WebSocket 协议

DungeonProtocol 只从连接登录态取得 username。`get_dungeon`、装备操作及 M3 挑战/控制/结算协议已经实现。所有响应携带 request_id，写入成功携带新 `profile_version`；挑战控制另携带当前 revision。

| 请求类型 | 主要字段 | 服务端行为 |
| --- | --- | --- |
| `get_dungeon` | request_id | 返回配置公开摘要、装备、穿戴、关卡进度、pending 数量和当前活动摘要；不推进挑战 |
| `dungeon_start` | request_id、challenge_id、difficulty_id、expected_version | 校验解锁、pending、活动锁；建立快照并开始 |
| `dungeon_sync` | request_id、battle_id、after_sequence | 补算到服务器当前时间，必要时结算，返回状态和事件页 |
| `dungeon_control` | request_id、battle_id、command、expected_revision | command 为 pause/resume/set_rate/abandon；set_rate 另带 rate |
| `dungeon_equip` | request_id、slot、item_id 或 null、expected_version | 校验物品与活动限制，原子替换槽位 |
| `dungeon_compare_item` | request_id、item_id | 使用服务端属性解析器返回当前、替换后及差值；不修改存档 |
| `dungeon_lock_item` | request_id、item_id、locked、expected_version | 设置明确布尔值，不使用切换动作 |
| `dungeon_sell_item` | request_id、item_id、expected_version | 原子消耗物品并通过钱包增加金币 |
| `dungeon_claim_items` | request_id、item_ids、expected_version | 将指定 pending 实例移入背包，无新增奖励 |
| `dungeon_get_result` | request_id、battle_id | 只读已提交结果；未结算返回当前状态，不相信客户端胜利声明 |

`get_dungeon` 返回 `dungeon_state`，动作返回 `dungeon_result`，事件页为 `dungeon_events`，错误为 `dungeon_error`。动作响应带 `result_kind="action"`，业务结果和最新状态分开；结算查询仍保留顶层 `battle/result`，带 `result_kind="lookup"`，以免破坏现有客户端。重放起局回执保留原操作结果，但其中 battle 刷新为当前状态。`dungeon_sync` 不把高频读取写入动作回执；其可重复执行性由 revision、事件主键、奖励唯一凭据保证。

示例请求：

```json
{
  "type": "dungeon_start",
  "request_id": "start-0001",
  "challenge_id": "ruins_slime_01",
  "difficulty_id": "normal",
  "expected_version": 3
}
```

示例错误：

```json
{
  "type": "dungeon_error",
  "request_id": "start-0001",
  "code": "pending_items",
  "message": "请先领取待领取装备",
  "retryable": false
}
```

至少实现 `auth_required / invalid_request / not_found / challenge_locked / active_job / pending_items / item_protected / inventory_full / version_conflict / state_conflict / request_conflict / invalid_config / unsupported_version / storage_failed`。越权的物品或挑战 ID 统一 not_found，不泄露其他账号状态。

每个请求在鉴权后限制字段类型、枚举和列表长度；同步默认同账号每秒最多 4 次，新开局每秒最多 1 次。多端共享活动记录，控制指令使用 expected_revision；另一端状态过期时刷新重试。推送仅发本人连接，禁止广播装备、种子或战斗记录到公共聊天。

## 9 五次通关扫荡

扫荡作为 v0.1.1 独立交付，必须在奖励、并发、断线恢复测试通过后开发，不依赖技能和打造。

- 同一 `challenge_id + difficulty_id` 累计五次手动挑战胜利解锁，失败不清零；x1 与 x2 都计数，不要求连续。
- 资格永久保存，换装不撤销。扫荡不增加解锁计数，不解锁新关卡，不触发首次通关奖励。
- 扫荡与战斗共用 `dungeon_active_jobs`；一个账号只能有一个未领取扫荡或活动挑战。
- 开始时冻结该挑战常规奖励配置、独立掉落种子、`ready_at`；不得使用领取时的新奖励表。
- 到期按服务器墙钟判定，离线照常计时；x2 不缩短扫荡时长。完成后领取，再开启下一次，不做无限续扫或批量预约。
- 奖励沿用对应挑战的常规奖励包和首领稀有保底，无额外虚构的整局奖励；后续多节点奖励另设新 challenge_id。
- 开始前有 pending 则拒绝；领取时满包仍提交金币和凭据，装备进入 pending。重复领取返回原包。

新增 `dungeon_sweeps(sweep_id, username, challenge_id, difficulty_id, status, snapshot_json, seed, ready_at, result_json, reward_token)`，status 为 `running / claimed`。到期未领取仍占活动记录，不依赖后台任务改状态；`ready` 可由时间推导。新增 `dungeon_sweep_start`、`dungeon_sweep_claim`，使用与挑战奖励相同的唯一凭据和事务原语，但独立的奖励来源 ID；届时将奖励表的来源扩为 `source_kind + source_id` 唯一键，旧记录回填 `battle + battle_id`。battle_id 对扫荡允许为空，保留其唯一索引及旧记录读取兼容；迁移需要重建表时在事务内复制并核对记录数。

每个关卡必须配置 `sweep_duration_seconds`，联调可先设普通 30、精英 60、首领 90 秒。线上值需结合主动挑战 x2 的单位现实时间收益评审；不得把建议值当作既定收益承诺。

## 10 界面与资源交付要求

### 10.1 页面闭环

1. 庄园入口打开地下城准备页：显示六槽装备、六项面板、已解锁关卡、敌人属性、奖励范围和通关次数。
2. 选择装备显示前后差值、售价值、保护状态；出售前显示本件和确定收益。
3. 开始后等待服务端返回 battle_id，再进入战斗页。双击按钮只发送同一个未完成 request_id。
4. 战斗页展示双方 HP、当前阶段、动作反馈、最近 100 条日志、暂停/恢复、x1/x2 和返回入口。
5. 返回庄园只是离开页面，挑战继续；“放弃本次挑战”单独确认，说明本次无奖励。两者不能共用一个含糊的退出按钮。
6. 结算页显示真实到账、待领取装备、时长、造成与承受伤害、通关次数；失败可调整装备或开始新挑战。

暂停和倍速按钮只有服务端确认后才显示为已生效；请求中保留旧状态并禁用重复操作。断线时停止本地向前猜测伤害，显示重连提示。服务端终态到达后可以跳过积压的非关键动画，但必须显示最终阶段与结算信息。

### 10.2 美术与移动端约束

玩家复用现有庄园外观，首轮只制作软泥、精英和首领等必要资源；不同普通怪可先采用经确认的变体。每个 visual_id 至少有待机、攻击、受击、死亡表现；缺资源时用明确占位图，不阻止结果展示。

手机 390 像素宽下血条、暂停和返回可操作，日志滚动不挤压战斗区域。暴击和阶段变化不能只用颜色传达；不依赖 hover 查看数值。动画仅消费事件，页面切走时释放定时器、监听器和音效，不能销毁服务端挑战。

### 11.2 存档 协议与体验验收

- 两个连接同账号同时起局，只有一个成功；两个账号可以独立战斗，互不泄露事件。
- 同 request_id 同参数返回原业务结果；更换参数拒绝；旧回执不覆盖新装备状态。
- 故障分别注入金币写入后、装备写入后、通关计数后和事务提交后的发送阶段；前三者全回滚，最后一种重连读取已提交结果。
- 有活动挑战时换装失败；装备 ID 越权、出售已锁定装备、重复出售均不会产生金币。
- 背包只剩一格却获得两件，第一件入包、另一件 pending；清理背包后领取保持相同 item_id。
- 暂停后进程重启仍暂停；运行中重启按原版本和锚点补算；不支持的模拟版本不改存档。
- 数据库锁冲突返回可重试错误，不把业务操作作为成功广播，不让两个 revision 覆盖彼此。
- 第四次胜利仍锁定扫荡，第五次解锁；不同难度/挑战分开计数，扫荡不增加次数。
- 断线扫荡到期可领；同账号战斗与扫荡冲突；重复领取、领取中满包不会丢奖。
- 新库和旧庄园库迁移均可重复执行；旧金币、农作物、工具和进行中的庄园活动数据保持正确；删除账号清理从属数据。
- 手机上血条、暴击文字、阶段与日志可读；暂停和变速不依赖帧率；打开装备详情无需悬停。

### 11.3 测试文件与运行方式

现有 `tests/test_dungeon_foundation.py`、`tests/test_dungeon_combat.py`、`tests/test_dungeon_equipment.py`、`tests/test_dungeon_runs.py`、`tests/test_dungeon_protocol.py` 覆盖 M0～M3，包括并发起局、重复补算、控制、奖励故障回滚和断线查询。M4 增加浏览器测试，扫荡独立增加测试。Python 测试使用临时库与注入时钟；浏览器测试接入现有 runner。

以下命令是各阶段的验收入口；M0～M2 的现有测试已覆盖目录、战斗、装备服务与协议，后续阶段继续补齐对应测试：

```bash
uv run --locked python tests/test_dungeon_combat.py
uv run --locked python tests/test_dungeon_foundation.py
uv run --locked python tests/test_dungeon_equipment.py
uv run --locked python tests/test_dungeon_runs.py
uv run --locked python tests/test_dungeon_protocol.py
uv run --locked python scripts/run_python_tests.py
npm run test:browser
```

经济模拟固定种子，每个“装备档次 × 遭遇”至少 1000 次，报告胜率、剩余 HP、平均及 P95 战斗时间、金币与掉落分布；不把一次好运结果作为难度结论。参考调试目标：普通 6～12 秒、精英 12～25 秒、一般首领 25～45 秒、最终首领 40～75 秒，均为模拟时间。当前只制作一个首领，先使用最终首领目标。

首轮可玩门槛为新手普通遭遇胜率至少 99%，推荐装备首领胜率至少 80%；若高配普通战太快，优先调整内容，不破坏攻速下限。纯模拟 180 秒首领在部署同级机器的 P95 目标低于 50 ms，每场不超过 10000 事件；超出目标先查无限行动、重复事件和配置，不能裁剪致死或发奖事件。

## 12 v0.2 扩展按依赖推进

本节保留旧稿有价值的方向，同时区分可直接继承的约束与尚需设计的功能。任何扩展先增加独立版本与测试，再修改线上配置。

### 12.1 第一批 技能与资源

先保持单武器，增加 MP、冷却、自动技能优先级。配置包含 `skill_id / tags / trigger / cooldown_us / resource_cost / target_rule / effects / priority`。每次行动先检查可行动条件，再筛选冷却、资源、目标和触发条件；按玩家优先级、配置序号、skill_id 排序。无技能可用时普攻，资源不足不进入冷却，行动成功才扣资源。

技能是否占用普攻时点、施法中被击杀、冷却起算、MP 恢复和打断规则必须在这一批规格中写明；没有这些规则不得开始法术动画开发。主副武器和专精不与首批技能同时上量。

### 12.2 第二批 状态与伤害类型

建立固定触发点与 EffectEngine，再引入物理/法术、抗性和首领技能。延续旧稿“物理只过防御、法术只过对应抗性”的方向；法强、法穿、施法速度及最终伤害乘区必须重新出统一公式与黄金测试，不将旧稿公式直接混入 v0.1。

状态实例至少保存规则 ID、source_actor_id、source_skill_id、母项 ID、数值、作用目标、到期时间或行动次数、叠层模式、当前是否生效。配置可描述不叠加、刷新、叠层、独立实例四种模式，首批内容只使用不叠加或刷新；其余模式完成上限与结算测试后再开放。状态时长不能同时混用秒数和行动次数。

先交付完整增益与 Debuff 列表，显示来源、代价、条件、覆盖关系和剩余时间；列表与结算使用同一状态数据。没有显示与归因能力，不继续增加复杂触发链。

### 12.3 第三批 随机装备与基础打造

在现有实例表新增底材 ID、阶位、物品等级、前缀/后缀实例、独特模板和回收档。旧装备按固定版本映射为兼容模板，保留已拥有属性；不随机重掷旧存档。

保留四品质适配方向：普通无词缀，优秀最多 1 前缀加 1 后缀，稀有最多 3 加 3，史诗固定机制模板。T1 为最高档；物品等级只决定合法词缀，不进入未定义的等级压制。先筛合法组，按组权重选组，再选合法档位及数值；同组互斥，池不足时允许少于容量上限。

打造先实现启灵、增缀、升格、拓印和少量定向精华。一次事务完成合法性校验、扣材料、固定随机结果、更新装备和幂等回执；无合法结果不扣材料，不支持通过断线重抽。装备已穿戴、锁定或被活动快照引用时禁止打造。材料、回收、兑换必须一起验证，避免“打造再分解”产生无限资源。

独特机制与装备联动在状态引擎成熟后接入；至少两个不同部位满足标签，联动全身一次，单件常驻数值仍算基础面板。完整套装、镶嵌、重组与异化继续后置。

### 12.4 第四批 多节点探索 肉鸽与天气

此批才将挑战改为多节点探索，使用新的关卡 ID、探索状态机和奖励口径，不复用单遭遇五次通关资格。开始设计时先确定跨节点 HP、撤离、已完成节点发奖和扫荡标准包的迁移方式。

保留旧稿的限制：玩家组合增益只来自装备联动、局内肉鸽、环境天气；肉鸽最多 6 项，同名不重复，满额只能替换或放弃；商店和事件不能绕过槽位。替换在同事务内扣局内货币、移除旧项及衍生状态、启用新项；已损失生命不返还，新增生命上限不自动治疗。

天气同时一类，地表同时一种；优先制作干燥、渗水和普通、潮湿、燃烧、带电水域。环境转换、作用双方、持续伤害归因和状态移除表单独交付。追加攻击、反击与持续伤害不继续触发同类连锁，设明确事件预算与失败诊断。

主副武器、专精、武器共鸣、多人和 PVP 不属于本规划的近期交付。只有单武器技能和装备已能产生可验证的构筑差异，才另开对应规格。

## 13 发布与维护

发布配置增加 `dungeon.enabled` 和灰度账号列表，默认关闭新入口与新开局。已存在挑战的查询、补算、结算和 pending 领取不受新开局开关影响，避免关闭功能后把奖励卡住。配置加载失败时只阻止新挑战，不破坏其他庄园玩法。

上线步骤为备份数据库 → 在测试副本重复验证迁移 → 部署兼容代码并启动 → 灰度账号完成起局、暂停、重连、结算、满包链路 → 核对金币流水与唯一凭据 → 放开入口。新增资源遵循现有页面版本参数策略更新缓存。

日志统一包含 battle_id、账号内部标识、配置版本、snapshot_hash、revision、request_id、错误码和耗时，客户端只显示可操作的错误信息。至少记录模拟耗时、事件量、结算重试、活动冲突、待领取积压、各关卡胜率与单位时间金币。

出现重复入账、丢失装备或旧快照无法恢复时立即关闭新开局，保留查询和领取。回退到能够读取当前存档的兼容版本，不直接删表或回退已提交金币；数据库备份恢复仅用于明确停服后的整体恢复，不与在线奖励混用。

文档、配置、界面文案、测试夹具和资源命名在合入前统一扫描禁用名称；引用参考文档时只使用本页开头的通用题名，不复制带人物指代的原始文件名、标题、首领名称或日志示例。
