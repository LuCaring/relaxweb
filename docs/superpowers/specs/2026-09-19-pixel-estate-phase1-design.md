# 休闲庄园：整体路线与第一阶段设计

日期：2026-09-19  
状态：产品设计已确认，等待实施计划  
适用仓库：`LuCaring/relaxweb`

## 1. 产品目标

在现有游戏厅中增加一个永久保存的单人经营游戏“休闲庄园”。玩家控制可移动角色，在同一张顶视角地图中经营农场、钓鱼和挖矿。庄园使用现有账号和站内金币：玩家购买土地、种子、工具、鱼饵和升级，也可以出售作物、鱼和矿石赚取金币。

庄园不涉及真实货币、充值或提现。经营所得不设置每日上限；经济平衡依赖购买成本、等待时间、工具耐久、内容解锁和固定售价。扣除成本后的收益全部归玩家。

第一阶段只实现庄园基础设施和农场，但地图从第一天就展示矿洞与湖边入口，使后续功能可以原地开放，而不是重新设计导航。

## 2. 已确认的产品原则

- 单人永久庄园，不是临时游戏房间。
- 农场采用类似经典网页农场的节奏：买种子、播种、等待、收获；不浇水、不枯萎，离线继续生长。
- 初始土地数量少，土地可购买并逐级升级；升级缩短该地块上作物的成熟时间。
- 钓鱼与挖矿是几十秒一局的主动玩法，分别在第二、第三阶段实现。
- 鱼竿和矿镐永久拥有，可升级；使用消耗耐久，耐久归零后花金币修理。种子和鱼饵是消耗品。
- 所有产品按服务端配置的固定价格出售。首版不做动态市场、订单、加工链、玩家交易或拍卖。
- 庄园等级通过经营经验提升。等级只负责解锁内容，解锁后仍需花站内金币购买，避免老账号用已有余额立刻跳过全部成长。
- 仓库容量有限，可花金币永久扩建。同类物品堆叠，容量按物品总数量计算。
- 角色可在地图上自由移动。桌面端使用 WASD/方向键，E、空格或鼠标执行交互；手机端使用虚拟摇杆和右侧操作按钮。
- 客户端移动和动画是本地表现；所有金币、库存、土地、等级、时间和奖励均以服务端状态为准。

## 3. 分阶段交付

### 第一阶段：庄园基础 + 农场

实现直接入口、永久存档、地图、角色移动、商店、仓库、庄园等级、土地、种植、离线成长、收获、固定价出售、桌面与手机适配。

### 第二阶段：钓鱼

增加鱼竿、鱼饵、耐久和修理。钓鱼采用鱼线张力玩法：按住收线、松开卸力，张力过高会断线，捕获进度填满后获得鱼。鱼竿等级影响容错，鱼饵影响鱼池和稀有度。

### 第三阶段：挖矿

增加矿镐、耐久、修理和矿层。每次下矿获得有限敲击次数，玩家在矿壁网格中选择石块，取得矿石、宝石、空洞或额外敲击机会。高级矿镐增加敲击次数并解锁高级矿层。

### 第四阶段：美术与完整回归

统一像素素材、环境动画、音效、装饰密度、性能和无障碍表现；完成桌面与手机人工验收、自动化浏览器回归、经济审计和现有功能回归。

每个阶段独立测试和提交。后续阶段不得要求重写第一阶段的数据边界或金币事务。

## 4. 接入架构

庄园作为独立持久化子系统接入现有服务器，复用登录、WebSocket、SQLite、金币余额和金币流水。它不继承 `BaseRoom`，不进入房间列表，不使用买入托管，也不参与多人游戏段位。

游戏厅新增“休闲庄园”卡片。其他游戏卡片仍进入房间列表；庄园卡片直接切换到庄园视图并请求当前用户的永久存档。

建议的后端边界：

- `estate/catalog.py`：作物、土地、仓库等级、解锁条件和价格的权威配置。
- `estate/schema.py`：庄园数据表初始化和向前兼容迁移。
- `estate/service.py`：读取快照以及购买、播种、收获、出售等事务操作。
- `chat_server.py`：只保留 WebSocket 鉴权、限流、消息适配和结果发送，不承载庄园规则。

建议的前端边界：

- `assets/js/estate/state.js`：庄园客户端状态和服务端快照合并。
- `assets/js/estate/map.js`：地图渲染、角色动画、碰撞、镜头和交互区域。
- `assets/js/estate/input.js`：键盘、鼠标、触摸和虚拟摇杆的统一输入接口。
- `assets/js/estate/ui.js`：HUD、土地、商店、仓库和错误提示。
- `assets/js/estate/protocol.js`：庄园消息注册与请求发送。
- `assets/css/estate.css`：HUD、弹层、移动端控制和安全区域样式。

该拆分让地图表现、业务状态和服务端经济规则互不依赖。后续钓鱼与挖矿可以增加独立模块，而不把第一阶段文件扩成单个巨型脚本。

## 5. 地图与输入

地图使用 HTML Canvas 绘制，HUD、弹层和控制按钮使用 DOM。Canvas 适合瓦片地图、像素精确缩放、角色动画和镜头移动；DOM 继续复用现有弹层、按钮、焦点和响应式布局能力。

地图规则：

- 使用 16×16 基础瓦片并按整数倍放大，设置 `image-rendering: pixelated`，避免模糊采样。
- 角色采用四方向待机和行走动画。
- 客户端使用固定时间步长更新移动，轴向分离的矩形碰撞阻止穿过建筑、水面、围栏和锁定区域。
- 镜头跟随角色，并在地图边缘停止滚动。
- 土地、商店、仓库、矿洞和湖边使用交互区域。角色进入范围后目标高亮，并显示统一操作提示。
- 打开商店或仓库时暂停角色移动；关闭弹层后恢复。
- 浏览器失焦、切换页面或打开输入框时清空移动按键，避免角色持续移动。

输入抽象输出统一的二维移动向量和 `interact` 状态：

- 桌面：WASD、方向键；E、空格或界面按钮交互。
- 手机：左下虚拟摇杆；右下大尺寸操作按钮。
- 钓鱼阶段复用操作按钮的按住和松开事件。
- 挖矿阶段允许直接触摸或点击矿壁格子。

第一版不实现点击地面自动寻路。该能力可作为后续辅助选项增加，不能成为地图交互的前置依赖。

## 6. 第一阶段数据模型

### `estate_profiles`

每个用户一行，保存庄园等级、当前经验、仓库容量、已解锁土地数量、创建时间和更新时间。首次进入庄园时惰性创建；初始化不收取金币。

### `estate_plots`

以“用户名 + 地块编号”为主键，保存土地等级、当前作物、播种时间和成熟时间。空地的作物和时间字段为空。锁定地块可以预先存在，也可以在购买时创建；服务层必须向前端返回统一的地块编号和锁定状态。

### `estate_inventory`

以“用户名 + 物品 ID”为主键，保存数量。数量降为零时可删除该行。容量按所有正数量之和计算；同类物品自动堆叠。

### `estate_actions`

以“用户名 + 请求 ID”为唯一键，保存动作类型、请求内容摘要、完成状态和可重放的动作结果。所有会改变金币、库存、土地或经验的请求都必须经过该表实现幂等。第一阶段不自动清理该表，避免删除仍可能被客户端重试的记录。

金币继续保存在现有 `users.coins`，审计继续写入 `coin_transactions`。庄园不得建立第二套余额。

## 7. 权威目录与数值约束

作物、土地升级、地块解锁和仓库扩容统一放在服务端目录中，客户端只接收展示所需的公开字段。目录项使用稳定 ID，保存中的 ID 不依赖中文名称。

作物配置包含：种子价格、出售价格、基础成熟秒数、固定产量、收获经验和解锁等级。土地等级包含：购买或升级价格、解锁等级和成熟时间倍率。仓库档位包含：扩容价格、解锁等级和目标容量。

具体数字在实施阶段通过独立配置评审确定，不写死在 UI 中。首轮数值必须满足以下约束：

- 每种作物在完整成熟并出售后具有正的单次净利润。
- 高等级作物可以提高单位现实时间利润，但同时提高本金占用和等待时间。
- 土地升级的回本周期明显长于单次收获，避免升级成为无成本的立即套利。
- 初始仓库足以容纳多轮基础作物，不迫使新玩家第一次收获前购买扩容。
- 初始可用土地保持少量，地图中可看到后续地块，但购买节奏不能由单次基础收获完成全部解锁。

第一阶段固定产量，不加入随机增产、暴击、天气、季节、施肥或病虫害。

## 8. 服务端数据流

### 首次进入

客户端发送 `get_estate`。服务端验证登录，惰性创建庄园资料和初始土地，随后返回 `estate_state` 完整快照。快照包含金币、等级、经验、仓库容量与用量、库存、土地、公开目录和服务器时间。

### 购买

客户端发送 `estate_buy`，携带请求 ID、商品类型、商品 ID 和数量。服务端按商品类型检查解锁等级、价格、余额、容量和购买上限。在一个数据库事务中记录幂等动作、扣除金币、写金币流水并增加物品或升级。土地只能在空闲时升级，升级不允许改变已经播种作物的成熟时间。成功后返回最新完整快照。

### 播种

客户端发送 `estate_plant`，携带请求 ID、地块编号和作物 ID。服务端确认地块已解锁且为空、种子存在，并在同一事务中扣除种子、记录播种时间，根据土地倍率计算成熟时间。

### 读取与离线成长

不创建后台定时任务。每次读取庄园时，服务端用当前时间与成熟时间比较并返回剩余秒数和是否成熟。服务器重启、用户离线和浏览器关闭不影响作物。

### 收获

客户端发送 `estate_harvest`。服务端确认作物已成熟并检查仓库容量。在同一事务中清空地块、增加固定产量、增加经验并处理连续升级。容量不足时不改变任何状态，作物继续留在土地上。

### 出售

客户端发送 `estate_sell`，携带请求 ID、物品 ID 和数量；另提供显式的一键出售动作。一键出售只处理目录中标记为可出售的农产品，不出售种子或后续阶段的工具。服务端检查库存，在同一事务中减少物品、增加金币并写“庄园出售”流水，然后返回最新快照。

所有成功变更返回完整权威快照和原请求 ID。客户端不得通过本地增量猜测最终金币或库存。

## 9. 并发、错误与恢复

- 购买、播种、收获和出售均使用数据库事务；涉及同一用户余额或存档的写操作在提交前重新读取当前状态。
- 相同请求 ID 重发时不再次执行；服务端返回第一次动作结果，并附带当前最新庄园快照。
- 请求 ID 已存在但动作内容不同，返回协议错误并记录安全日志。
- 多标签页同时操作同一土地时只有第一个满足条件的事务成功，另一个收到最新庄园快照。
- 余额不足、等级不足、仓库已满、地块锁定、地块非空、作物未成熟和库存不足都使用稳定错误码，并附中文提示。
- 网络断开前结果已经提交但客户端未收到时，客户端使用原请求 ID 重试即可恢复结果。
- 客户端收到比当前版本旧的快照时忽略；快照包含单调递增的存档版本号。
- 服务器异常不得部分扣款。事务失败时金币、流水、库存、土地和经验全部回滚。
- 仓库满时禁止会增加库存的购买；收获保持在地块上。后续钓鱼和挖矿在开始前按该次玩法可能产生的最大物品数量预留容量。

## 10. 界面设计

桌面和手机展示同一庄园地图。顶部 HUD 显示站内金币、仓库用量、当前快捷物品、庄园等级和经验。底部快捷栏在桌面显示更多槽位，在手机精简为当前物品、背包和更多按钮。

地图首期包含：

- 种子商店：购买种子、土地、土地升级和仓库扩容。
- 仓库：查看数量、单项出售和一键出售。
- 农田：显示空地、成长阶段、剩余时间、成熟高亮和锁定状态。
- 矿洞与湖边：地图中可见并可接近，第一阶段显示庄园等级与后续开放说明，不进入空白页面。

所有重要动作使用现有自绘弹层，不使用原生 `alert`、`confirm` 或 `prompt`。操作反馈在目标附近和 HUD 中显示，错误不会让角色输入失焦后卡住。

## 11. 美术方向与许可

美术采用“精致平衡”为主、环境细节靠近丰富华丽的方向：道路、土地、商店、仓库、矿洞和湖边保持清楚，树木、花草、水面、建筑纹理、阴影和小动画提供层次。视觉气质可以参考温暖的田园像素经营游戏，但不得复制任何现有商业游戏的角色、地图、建筑、UI、贴图或调色板。

素材使用规则：

- 优先使用 CC0 或明确允许随公开源码仓库再分发的素材。
- “允许用于游戏”不自动等于“允许把原始素材放入公开仓库”；实施前必须检查再分发条款。
- 每个外部素材在 `assets/estate/ATTRIBUTION.md` 记录作者、来源 URL、许可证、下载日期和本地文件范围。
- 许可证要求署名时，在仓库和游戏内鸣谢页同时保留。
- 来源不明、仅允许个人使用、禁止再分发或与仓库许可冲突的素材不得提交。
- 设计阶段使用的素材包宣传图只作为视觉参考，不进入正式产品资产。

## 12. 测试与 PR 门槛

### 领域单元测试

覆盖首次建档、目录校验、购买、播种、服务器时间成熟、离线读取、收获、出售、土地升级、地块解锁、仓库扩容、容量边界、经验升级和连续升级。

### 经济与并发测试

覆盖余额不足、仓库已满、未成熟收获、重复请求、相同请求 ID 不同内容、并发标签页、事务中途失败、断线重试和服务器重启。测试必须证明不存在重复扣款、重复收获、负库存或无流水金币变化。

### WebSocket 协议测试

使用临时数据库完成“注册或登录 → 进入庄园 → 购买种子 → 播种 → 推进测试时钟 → 收获 → 出售”的真实连接流程。测试时钟只通过依赖注入进入庄园服务，正式运行始终使用服务器真实时间。

### 桌面 HTML 测试

Playwright 验证键盘移动、碰撞、镜头、交互提示、商店、土地、仓库、HUD、弹层焦点和断线恢复。

### 手机 HTML 测试

Playwright 以常见手机视口验证虚拟摇杆、操作按钮、触摸取消、横竖屏、安全区域、滚动锁定和 HUD 不遮挡交互目标。

### 回归测试

现有德州、UNO、掼蛋、麻将、段位、签到、竞猜、转账、前端静态检查和协议测试必须继续通过。

### PR 硬门槛

提交 PR 前必须同时满足：

1. 本地静态服务和真实 WebSocket 服务上完成桌面人工验收。
2. 在真实手机或触摸模拟视口完成手机人工验收。
3. 庄园新增自动化测试全部通过。
4. 现有自动化测试全部通过。
5. 资产来源与许可清单完整。
6. PR 中不包含设计原型目录 `.superpowers/` 或仅用于比较的宣传图。

## 13. 明确不在第一阶段实现

- 钓鱼和挖矿的可玩逻辑。
- 天气、季节、浇水、施肥、枯萎、偷菜或好友访问。
- 动态价格、订单、加工、制造、玩家交易和拍卖。
- 点击地面自动寻路。
- 多人同步角色、庄园排行或段位联动。
- 真实货币、广告、充值、提现或可兑换奖励。

这些功能如需加入，必须单独设计并评估对金币产出、数据库迁移、资产许可和移动端交互的影响。
