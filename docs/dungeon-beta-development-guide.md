# 地下城 Beta 开发指南 V0.2

日期：2026-09-24。用途：分发给开发成员，统一方向、分工和验收。本文是建议采用的开发基线；其中“已确认”来自产品负责人本次补充，“建议基线”允许团队评审调整。本文不表示框架、接口或交易功能已经实现。

配套阅读：[架构方案](dungeon-beta-architecture.md)、[接口与插件合同](dungeon-beta-contracts.md)、[当前实现状态](dungeon-beta-implementation-status.md)。本指南是当前产品与协作基线。

2026-09-25 开工更新：首批公共底座与三条开发线的实际入口、验收结果见[实现交接记录](dungeon-beta-implementation-status.md)。下文描述完整 Beta 目标，不能据此认为动作战斗和交易已经上线。

## 1. 先读这一页

**本轮目标是交付能玩、能成长、能交易的短局版本，并让后续改玩法主要通过内容配置与有限的机制插件完成。** 不等待全部天赋、装备、资源和数值定稿后才开发，也不以插件框架本身的规模作为完成度。

### 已确认的大方向

1. 俯视2D自由移动，参考土豆兄弟、元气骑士的动作刷怪与局内构筑体验。
2. 永久装备刷宝＋局内肉鸽；长剑草稿是首个武器设计参考。
3. Beta 在游戏厅提供与庄园平级的入口，暂不并入庄园地图或庄园流程。
4. **共用现有账号和金币。金币是升级等成长动作的重要消耗材料，不建立第二套永久金币钱包。**
5. **支持玩家之间交易装备等资产。** Beta 先把装备与金币的真实成交闭环做可靠，再扩展交易资产种类。
6. 局内可以有其它货币，为商店、事件、重抽等服务。
7. 先做可玩版本再调整细节；拆成2～3条开发线，由我们承担主要框架，各组在约定边界内决定具体玩法。

### 首版实验范围

Beta先做8～12分钟短局、少量代表内容。金币是永久成长的重要成本，辅助材料按需配置；局内货币用于商店、事件和重抽。暂定的装备槽、强化次数和局内换装限制均可在框架边界内调整，不要求实现完整长剑节点表。

经济共用意味着玩家可能带着较多既有金币进入 Beta。建议以关卡/专精进度决定可升级范围、金币承担主要费用，辅助材料用于定向追求。已有金币应有用，但不直接购买尚未开放的所有机制。这是本轮建议，不擅自限制原有账号余额。

## 2. Beta 的完成定义

可交给非开发成员体验的 Beta，必须串起：

```text
游戏厅 → 地下城准备页 → 战斗与局内选择 → 成功/失败结算
       → 获得装备 → 用共享金币升级/改造 → 再次挑战
       → 向另一玩家发起装备报价 → 对方确认成交 → 双方资产正确更新
```

最低内容建议：1个角色、1类主武器（长剑）、至少2种可辨识打法、3～4种普通敌人、1个首领、3个普通房＋1个首领房、6～10个局内强化、一个小型装备池、至少一个使用金币的成长动作。共鸣可先做1槽/2条效果；如果影响首个闭环交付，可在内测阶段关闭，对外标注未开放。

这些数量是排期起点。各组可以在同等可玩性和工作量内换方案，但不能把交易、可靠发奖、金币扣除或重连数据正确性当作“数值未定”而省略。

### 两种运行环境

| 环境 | 允许内容 | 资产边界 |
| --- | --- | --- |
| 内部玩法原型 | 固定预设、调试加速、纯本地模拟、占位美术 | 必须使用测试库/隔离资产，不写正式金币与可交易装备 |
| 对玩家开放的 Beta | 框架认可的权威战斗结果、正式金币成长和交易 | 所有永久资产通过服务端事务；不接受客户端自行申报掉落/胜负 |

“能看见动作”是内测阶段成果；“能连接正式金币与交易”必须过资产验收。这两道门槛可以先后完成，不要求第一天做全。

一旦使用正式共享金币并允许交易，就不能按普通测试存档随意清空已消费金币或已成交装备。玩法仍可改，但存档变化走版本迁移；确需回收/补偿时逐笔可追溯，不能删除流水后假装没有发生。可随意清档的实验保留在测试库。

## 3. 三条并行线：谁负责什么

推荐三线，总体框架由 A 线负责。按角色分工，不预设具体成员姓名。

| 开发线 | 主要负责人 | 交付内容 | 自主裁量范围 |
| --- | --- | --- | --- |
| A 框架、存档与交易 | 我们/框架负责人 | 从庄园命名空间解耦、合同/注册器、命令事务、共享钱包适配、装备归属、升级应用服务、报价成交、版本/存档、模拟器宿主、联调工具 | 内部实现和基础设施选型；遵守现有部署与数据兼容 |
| B 动作战斗与客户端 | 战斗/前端/美术成员 | 游戏厅入口、独立页面、移动/瞄准/闪避、战斗模拟插件、敌人AI、表现、局内选择UI、装备/升级/交易页面 | 手感、房间节奏、动作参数、UI和美术；不得自行发永久奖励 |
| C 成长内容与经济 | 策划/内容开发成员 | 武器/词条/强化/掉落/成长/商店配置包，金币消耗与产出方案，首局体验、代表构筑与验证场景 | 节点取舍、数值、掉落结构、局内货币、升级路线；新规则走能力申请 |

B 线的模拟代码运行于服务端权威模拟接口；客户端只预测获准的运动状态和表现。A 线提供时钟、输入队列、随机源、存档与运行容器，B 线不需要自己解决数据库、交易或 WebSocket 连接管理。

若只有两组：A 负责框架、交易和共享经济规则，B 合并动作/客户端/内容配置；仍保留三块目录和审查责任，避免未来拆组时再改边界。A 先提供固定测试内容，不能让B等完整经济设计才能开工。

### 文件所有权建议

以下为目标目录，当前不存在的路径须由 A 首次创建；具体映射见架构方案。

| 路径 | 主维护线 | 协作规则 |
| --- | --- | --- |
| `dungeon/contracts/`、`contracts/dungeon/` | A | B/C可提需求；字段变化先更新合同与fixture |
| `dungeon/application/`、`storage/`、`runtime/` | A | 金币、资产、交易、模拟宿主集中在此 |
| `dungeon/simulation/`、机制/AI内置插件 | B | 只通过已声明能力访问规则与状态，不引用钱包或数据库 |
| `assets/js/dungeon/`、`assets/css/dungeon.css`、`assets/dungeon/` | B | 复用已有UI分支，补充资产页面和动作渲染 |
| `content/dungeon/packs/` | C | 只放规则数据，修改自动触发内容校验 |
| `content/dungeon/release.json` | A汇总发布 | C提出内容版本；A统一组成可上线规则集 |
| `server/app.py`、`server/schema.py`、`server/wallet.py`、管理工具、部署入口 | A | B的大厅入口变更可独立PR，由A核对接入 |
| `tests/test_dungeon_beta_*.py`、浏览器测试、fixtures | 按功能归属 | 接口样例由A维护，功能验收由交付线补齐 |

不要由三组同时修改一个巨型 `catalog.py`、`service.py` 或 `view.js`。内容按包拆，业务按用例拆；确实需要共同变更时，先合接口，再合调用方。

## 4. 冻结边界，放开细节

| 必须统一 | 组内可以先实现再试玩调整 |
| --- | --- |
| 用户身份、金币单位、归属与物品实例ID | 武器伤害、攻速、射程、前后摇 |
| 金币与装备同事务；重复请求不重复扣款/发奖 | 升级费用曲线、掉落权重、商店价格（经共享经济回归） |
| 客户端不决定永久结果 | 自动攻击/手动瞄准细节、闪避手感 |
| 事件来源、触发上限与结算顺序语义 | 哪些词条/节点进入Beta、哪些先做预设 |
| 配置/协议/模拟/存档版本与兼容性 | 单局时长、房间编排、敌人搭配 |
| 交易时装备被预留，不能同时卖、分解、升级、穿戴或用于新开局 | 交易界面的布局、筛选、确认文案 |
| 所有可执行扩展经过白名单注册与测试 | 组装已支持效果、组合局内货币和事件选项 |
| 重连恢复规则、存档检查点、奖励唯一凭据 | 特效、音效、镜头与信息呈现 |

V0.1中的60点、17点核心门槛、三剑式结构可继续试验；不要将其直接编码为通用引擎中的常量。专精拓扑、经验曲线和解锁策略由内容包声明。修改正在使用的规则需发新内容版本，不能在同一版本上覆盖。

### 新规则申请只需说明六件事

“玩家得到什么体验；触发事件；需要读/写的战斗状态；参数及单位；重复/递归/移除规则；一个正例与一个反例”。

已有能力能表达的由 C 改数据；缺少纯战斗操作的由 B 加机制插件；涉及钱、装备、交易、存档和协议的由 A 增加应用用例。不能把任意脚本字符串塞进配置绕过这条分工。

## 5. 共享经济与交易的 Beta 口径

### 5.1 货币和成长

- 全站金币使用现有钱包，地下城不维护第二份“可消费金币余额”。
- 升级/改造配置必须能包含金币成本；Beta 至少开放一个实际消耗金币且有可感知效果的动作。
- 配方支持“金币＋零种或多种材料＋进度条件”，材料是否可交易逐类声明。
- 局内货币记录在当前 run 中，只用于局内商店、事件、重抽等。默认结算清零、不交易、不兑换金币；以后若要兑换必须新增有预算和记账的结算规则。
- 新手必须能用初始装备和基础金币/挑战收益开始循环；避免必须先在庄园打工才玩得动。
- 金币富裕玩家可以更快负担费用；机制开放与最高升级阶段仍可受挑战进度控制。禁止背地里针对账户余额抬价。
- 免费重配专精可保留；不要为“金币重要”而让每次试打法都产生费用。金币优先消耗在装备升级、改造、制作和交易手续费。

C线提交经济参数时，至少比较新账号/已有少量金币/已有较多金币三种起点，输出“首个升级需要几局、连续失败能否继续、金币净产出/分钟、制作拆解是否套利”。金币消耗和产出均进入全站经济，不能只平衡地下城自己的小循环。

### 5.2 先做定向固定价交易

推荐 Beta 最小交易：**卖家选一件装备、指定买家、填写金币价格；装备被预留；买家看到物品快照、总价和手续费后确认；系统一次完成双方金币变动与装备转移。**

这已经是真实玩家交易，不要求首版同时做全服拍卖行、竞价、离线搜索、以物易物和撮合引擎。后续扩展资产种类沿用资产策略接口；Beta必须至少支持装备。普通可用装备默认可重复交易；新手赠品、测试物品与明确绑定物品例外，属性界面必须显示原因。

- 一次报价一件装备、一个指定买家、一种结算金币，价格/手续费/到期时间在创建时冻结。
- 不允许买自己的装备；未接受前可撤销；到期后不可接受，系统释放预留。
- 买家金币不足，失败且不扣钱；背包满则成交物品进入待领取，不能先付钱后丢装备。
- 卖家在接受前不先收钱；创建报价不扣买家金币。价格修改通过撤销旧报价、创建新报价完成。
- 手续费初始比例由C线建议，A线实现并记录销毁/去向。客户端展示买家总支出与卖家净收入，不能用“系统税”隐藏收费。
- 报价的物品不能被升级、分解、NPC出售或在其它报价重复使用；所有旧入口也必须遵守。
- 取消与接受并发时只有一个成功；买家断线重发不再扣一次；成交后卖家不再拥有该物品。

## 6. 并行推进顺序

### 第一道交接：A交付最小公共底座

A优先交付合同V1、模拟器接口、内容schema、固定fixture/假服务、错误码、资产写入服务、可跑的最小页面接入说明。不是等A写完所有交易和运行时才允许B/C开工。

| 阶段 | A 框架 | B 战斗/客户端 | C 内容/经济 | 合流验收 |
| --- | --- | --- | --- | --- |
| F0 公共底座 | 解耦薄壳、合同与fixture、插件注册/内容校验、共享钱包端口 | 复用UI分支，连接fixture，完成大厅入口和页面导航 | 一份最小长剑/敌人/成长内容包 | 三线读取同一合同版本；旧地下城仍可回归 |
| F1 可玩短局 | 运行宿主、权威输入、检查点、奖励事务 | 移动/战斗/敌人/首领/局内选择、胜败显示 | 2种打法、代表词条、房间/局内货币配置 | 完成短局，断线恢复，正式奖不依赖客户端结论 |
| F2 成长与交易 | 金币升级、资产预留、定向交易、幂等/故障验证 | 装备、升级报价、交易发起/接受/待领取UI | 升级费用、掉落/贸易属性、经济测算 | 两账号完成打宝→升级→交易，重复请求无资产变化 |
| F3 开放 Beta | 迁移/回滚演练、监控、功能开关与发版清单 | 浏览器实测、可读性、性能、异常状态 | 真人试玩调参、配置版本与回归场景 | 验收清单通过，三线使用同一发布规则集 |

F1和F2的无依赖部分并行做；只有F1通过不能宣布对玩家开放 Beta 已完成。排期按里程碑估工，不承诺未经团队确认的天数。

## 7. 分支与合并规则

三条开发线统一使用 `dev/` 前缀，从公共底座 `8309c0e` 及文档整理提交分出，各有独立开工提交：

| 线 | 分支 | 处理方式 |
| --- | --- | --- |
| A | `dev/dungeon-beta-foundation` | 框架开发及Beta集成，由A审阅公共合同与跨线合并 |
| B | `dev/dungeon-beta-client` | 动作模拟、独立大厅入口、客户端；选择性复用旧UI |
| C | `dev/dungeon-beta-content` | 内容包、成长、经济样例；通过现有校验器验证 |

原本地 `dev/dungeon-core` 已并入A线后退役，三个 `codex/` 名称已替换。远端旧core/UI引用没有改写或删除；旧UI的两笔独有提交保留在本地标签 `archive/dungeon-ui-before-beta`，供B/C检查复用，不再作为新任务的开发起点。当前只完成本地分支整理，发布远端分支时再处理远端交接。

A线兼任集成，避免另留一条无人维护的core分支。B/C通过审阅后合入A，公共合同更新先在A落地，再由B/C普通merge同步。各分支的开工说明位于：A的 `dungeon/application/README.md`、B的 `dungeon/simulation/README.md`、C的 `content/dungeon/README.md`；对应文件随各线首个提交加入。查询实时HEAD使用 `git log --graph --decorate --oneline --branches='dev/dungeon-beta-*'`，不把会变化的HEAD写成固定文档版本。

UI旧目录扩充转成新内容包；旧协议和事件播放器只能用于兼容参考，不能直接充当动作模拟。不要整支覆盖当前框架和素材变更。

- 协议变化先交schema/fixture/错误码，再分别改B和C；新增可选字段保持兼容，破坏变更升级协议版本。
- 功能PR保持纵向可验收，例如“一个可注册的减速效果＋一件示例物品＋测试”，不一次交空目录框架。
- 共享分支更新优先普通merge，不强制改写成员已共享的历史；避免最终一次性大合并。
- 每个PR写清：依赖基线、合同/规则版本、修改的公共接口、测试命令、存档影响、可玩的演示路径。
- 需要另一线未合功能时明确依赖提交；合入集成分支前验证整条路径，不让双方各自假定对方已实现。

## 8. 可直接分发的首批任务

**给 A：**基于现有内容加载器、升级服务和资产门禁，先接鉴权升级协议与错误映射，再实现权威运行宿主、房间奖励与原子成交。完善运行和交易fixture，统一迁移编号、公共接口与发布规则集。

**给 B：**盘点 `archive/dungeon-ui-before-beta` 保留的页面，接入游戏厅平级入口；按模拟接口实现短局动作玩法与服务端可运行的模拟插件，前端先接fixture完成战斗、装备、升级、交易异常态。自由决定手感和表现，提交两套可区分打法及首领演示，不依赖完整132节点。

**给 C：**扩展已存在的最小Beta内容包，包含长剑、两个打法预设、普通敌人与首领、局内强化、掉落与金币成长成本；写出新号/富号/失败路径的经济样例。每个新机制附触发边界和演示种子，现有能力不能表达时向A/B提能力需求，不直接改钱包/SQL。

## 9. 对外 Beta 必过验收

- 从游戏厅进入地下城；不需要先进入庄园；使用同一账号与金币余额。
- 普通玩家能完成短局，至少两种构筑可辨识；成功/失败都有明确状态和去向。
