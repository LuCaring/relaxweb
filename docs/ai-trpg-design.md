# RelaxWeb 在线 AI 跑团：调研与实施方案

调研日期：2026-09-23。本文区分已核实事实、建议设计与已完成验证；尚未接入线上游戏厅。

## 1. 建议决策

在现有 Python + SQLite + 原生 ES Module 架构内新增独立的持久化战役模块，复用账号、WebSocket 和大厅导航。以 DeepSeek 官方 `deepseek-flash` 作为 AI DM，以服务端规则引擎和数据库作为游戏事实的唯一来源。

首版支持中文、邀请制小队、预设角色、自然语言行动、检定、基础战斗、自动存档和继续冒险。先完成一部冒险，不同时建设通用模组市场、完整 D&D 编辑器或多规则平台。

推荐分工：

- **模型**：理解行动意图、扮演 NPC、提出需要的检定、根据确定结果叙事。
- **规则代码**：决定允许的动作、检定修正、骰子、攻击/伤害、资源消耗、任务状态迁移。
- **数据库**：保存角色、场景、公开/秘密事实、游戏内时间、待处理行动、骰点和提交版本。
- **前端**：呈现玩家有权看到的状态、行动选项、骰点和回放；断线重连后向服务端恢复。

Diceframe 用作玩法和架构参考；首版复用小型开源组件，不直接复制其引擎源码。

### 《追捕克仑可》对引擎的要求

- 第 2 页规定原版面向 **4–6 名 1 级角色**，完成后可升至 2 级。单人操作一支预设小队可以作为试跑模式；单角色版本需要明确的遭遇重平衡，不能直接沿用原版人数与伤害。
- 第 3–8 页形成委托、卷宗、联络人、街头消息、下水道和军火商等调查分支。需要线索图和角色已知信息，不能把所有场景写成强制顺序。
- 第 5 页有跨数日的事件时间线。时间只随调查、旅行、休息等游戏行动推进；用户离线或服务器停机不能让游戏世界自动跳到坏结局。
- 第 3、13 页包含开局选定或暗骰产生的幕后关系。应在开局落库，随后保持一致，并作为 DM 私有信息。
- 第 9–12 页的仓库涉及岗哨换班、增援、上下层、陷阱、可破坏结构、机器和 NPC 资料卡。第一版可用地点节点及高低层关系表示，后续再做方格战术地图。
- 第 13 页包含逃跑、抓捕、交涉、移交与后续关系。目标是活捉，必须支持非致命近战击倒、俘虏状态和分支结局，不能仅提供“击杀获得奖励”。

### 导入前需要解决的具体问题

1. **资料不完整**：冒险第 3 页明确依赖其他规则书；例如第 10 页的地精头目、第 13 页的老兵，以及部分物品并没有在这两份材料中完整给出。生成 `unresolved_references` 清单，补齐可用的资料或明确采用简化替代。禁止自动让 LLM 填数值后当作原版。
2. **时间矛盾**：第 5 页的订单/交货安排与第 8 页“逃脱当天日落送货”的描述存在冲突。导入器标记冲突；建议场景包统一按第 5 页时间线，并记录该编辑决定，正式开团前复核。
3. **正文与秘密混排**：开场朗读、检定门槛、幕后真相、怪物数据必须拆开。原文分页引用保留到每个条目，以便校对。
4. **内容分发边界**：冒险页脚明确带有 `DO NOT DISTRIBUTE`。当前仅本地分析；PDF、插图和全文抽取不进入公开 `assets/` 或仓库。公开发布所用的剧本正文和素材需确认可用范围。通用规则数据可优先评估官方公开 SRD，但 SRD 不等同于这份冒险或其中文翻译的授权。[官方 SRD](https://www.dndbeyond.com/srd)

### 为什么不直接注册为现有牌桌

当前 `RoomHost.game_rooms` 在内存中维护房间，并存在成员离线、房主离开后的离桌/解散及金币结算机制。`Application.run()` 重启恢复的是托管退款与竞猜，并没有恢复完整牌局引擎。长战役需要独立的生命周期，不能把“房间仍在内存中”视作断点继续。

沿用 README 中普通牌桌玩法通过 `games.base` 注册的约定；跑团作为新的持久化业务域，接入方式更接近庄园的独立协议。两者共享大厅，但战役退出只取消订阅，不删除角色或存档。跑团内 gp/奇诺属于战役资源，与网站钱包、买入和段位结算分开。

建议目录：

```text
trpg/                         # 纯领域逻辑，不导入 server
  models.py                   # 角色、战役、意图、事件契约
  rules/dnd5e_starter.py       # 锁定所采用规则版本与支持范围
  dice.py                     # d20 封装和表达式约束
  scenarios.py                # 场景图、时间线、版本校验
  views.py                    # 玩家/房主/旁观者可见信息
server/trpg/
  protocol.py                 # 鉴权、消息校验、应答
  service.py                  # 回合阶段与后台任务编排
  repository.py               # SQLite 原子事务、事件和快照
  provider.py                 # DeepSeek 异步适配
  context.py                  # 规则、事实、摘要和最近历史
assets/js/trpg/               # ES Module 界面
data/trpg/scenarios/          # 私有内容，不属于 assets，不进 Git
```

生产实现时为 `data/trpg/` 增加忽略规则，配置绝对路径，并纳入私有备份流程。不要把 API Key 加入 `client_config()`。

## 5. DeepSeek 官方接入

官方文档在调研日确认：V4.1 Flash 的模型 ID 为 **`deepseek-flash`**，API Base URL 为 **`https://api.deepseek.com`**，支持 OpenAI 兼容接口。旧 `deepseek-v4-flash` 名称为兼容路由；不要自行拼成 `deepseek-v4.1-flash`。[首次调用](https://api-docs.deepseek.com/zh-cn/)、[发布说明](https://api-docs.deepseek.com/zh-cn/news/news260910/)

建议生产端先使用异步 HTTP 客户端调用 `POST /chat/completions`，只接这一家服务时无需 LiteLLM 或完整 Agent 框架。Key 使用 `DEEPSEEK_API_KEY` 环境变量，模型名可通过 `DEEPSEEK_MODEL` 覆盖。部署配置更新需要重启服务，Key 不写入存档、日志或前端。

### 两阶段模型工作

1. **意图/计划阶段**：输入当前场景、允许动作、当前角色、玩家声明与必要规则；输出有限 JSON/工具参数，例如 `propose_check(actor_id, skill, reason)`。实体 ID、技能、动作次数、检定修正和 DC 由规则层验证；模型不能把玩家文字直接翻译成任意 SQL/JSON Patch。
2. **结算/叙事阶段**：服务端保存检定和资源消耗方案后，把确定结果提供给模型，生成公开描述。只有通过校验的领域事件才能更改权威状态；“你得到了 100 金币”这种自由文本没有执行权。

对规则已知的按钮操作（攻击、休息、施法）可以跳过意图调用，减少延迟与成本。探索中的新颖行动允许 DM 提议 DC 和后果，但必须落入已定义的裁决范围；规则未支持时返回澄清或明确提示简化处理，不静默编造规则。

工具调用首版限制在 3 个循环以内，每轮设置模型调用次数和输出上限。JSON 合法不等于业务合法，还要做类型、范围、对象归属、角色行动资格、场景前置条件和资源余额校验。错误输出允许一次修复，仍失败则暂停该回合。

普通叙事建议显式关闭思考，复杂规划再比较低强度思考的质量和延迟。官方当前默认开启思考；携带 tools 时，对 `reasoning_content` 的回传要求与普通聊天不同，适配器必须保存该阶段的完整模型消息和工具结果，并按官方文档重建请求。推理内容不作为玩家日志广播。[思考模式](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)、[工具调用](https://api-docs.deepseek.com/zh-cn/guides/tool_calls/)

服务端为每个战役串行推进，同站点设置全局并发上限。429/5xx 可退避重试；鉴权和余额问题提示管理员处理。外部调用不能持 SQLite 写事务，也不能阻塞整个 WebSocket 连接读取循环：先持久化命令并应答，再交给受生命周期管理的后台任务。

### 上下文与长期记忆

建议初始上下文预算 12k–24k tokens，后续按实测调整：固定规则摘要、场景局部材料、权威状态、带来源的阶段总结、最近 6–10 个完成回合。长期原始日志完整保存，但不逐轮无限增长地回传。

- 总结保存 `through_event_seq`、`prompt_version`、角色/可见性范围；只能由已提交事件生成。
- HP、背包、已获得线索、人物生死、关系和事件时间来自结构化状态，摘要不能覆盖这些事实。
- 首版用场景 ID、NPC ID、关键词与邻接节点检索。中文搜索不假设 SQLite 默认 FTS 分词足够好；先采用作者标签和实体关联。向量检索作为后续可选项，不假定聊天模型提供 embedding API。
- 面向玩家的叙事上下文只注入该玩家/队伍获准获知的信息；携带秘密的规划器只输出受校验的计划。不要先将整份秘密剧本交给叙事模型再依赖前端隐藏。
- DeepSeek Responses API 文档明确说明接口无服务端会话存储；上下文缓存也不是存档。战役恢复完全依靠自己的数据库。[官方说明](https://api-docs.deepseek.com/api/create-response/)

按 usage 记录输入、缓存命中、输出与累计费用估算；限额可以先按 tokens 实施，价格维护成配置。使用调研日[官方价格表](https://api-docs.deepseek.com/quick_start/pricing/?push_animated=1&show_loading=0&theme=light&webview_progress_bar=1)计算，不把价格硬编码进规则引擎。尚未实测模型的延迟、质量或真实费用。

## 6. 断点继续的事务设计

“保存聊天记录”不足以恢复正在处理的回合。最低要求是刷新、断网、模型超时、服务重启和重复点击均不重复掷骰、扣血或发奖励。

```mermaid
flowchart LR
  A[登录并提交行动] --> B[保存命令与幂等键]
  B --> C[规划与规则校验]
  C --> D[持久化检定与骰点]
  D --> E[生成并校验叙事]
  E --> F[同一事务提交事件 状态 日志]
  F --> G[按权限推送及重连补发]
  D --> H[中断或超时]
  H --> E
```

### 建议表结构

| 表 | 关键字段与约束 |
| --- | --- |
| `trpg_campaigns` | UUID、owner_user_id、scenario_id/version/hash、ruleset_version、prompt_version、status、revision、game_time、state_json、schema_version |
| `trpg_members` | campaign_id、user_id、role、character_id、active；成员资格独立于在线状态 |
| `trpg_characters` | 身份归属、属性、技能、HP、AC、法术资源、背包、状态；也可首版放入 state_json，避免两份可写真相 |
| `trpg_commands` | command_id、campaign_id、user_id、client_action_id、payload_hash、base_revision、phase；唯一 `(campaign_id,user_id,client_action_id)` |
| `trpg_turns` | turn_id、campaign_id、base_revision、phase、plan_json、provider_messages_json、attempt、lease_until、lease_token、error_code |
| `trpg_rolls` | turn_id、check_id、expression、raw_dice、total、rule_ref、visibility；唯一 `(turn_id,check_id)` |
| `trpg_events` | campaign_id、seq、turn_id、event_key、type、visibility、payload；唯一 `(campaign_id,seq)` 与 `(turn_id,event_key)` |
| `trpg_snapshots` | campaign_id、revision、schema_version、state_json、checksum；初期可每回合保存，后续按间隔压缩 |
| `trpg_summaries` | campaign_id、scope、through_event_seq、summary、prompt_version |

状态 JSON 只是存储格式；所有写入必须经过领域规则。建库时按现有迁移模式执行；外键需要确认每个连接启用，不能仅声明 `REFERENCES` 就假定生效。成员引用稳定 user_id，并补充账号注销时的转交/匿名化策略。

### 回合阶段与恢复

1. 收到命令，鉴权并核对 `expected_revision`。在短事务中写入幂等键、原始行动及 payload hash 后返回 `accepted`；相同键同载荷返回已有进度，不同载荷返回冲突。
2. 一个战役同时只有一个结算者。单进程使用战役锁，数据库使用状态条件更新；若使用 worker 租约，提交必须验证递增的 fencing token，阻止租约过期的旧任务提交。
3. AI 计划通过校验后持久化。为每项检定分配稳定 check_id；骰点和计划一同保存完成才进入叙事。重试只能读取既有骰点，不重新生成计划里的已完成随机结果。
4. 网络请求在事务外执行。输出先暂存为草稿，完成并验证后，以 `revision = base_revision` 的条件更新在**同一事务**内写入状态、事件、最终叙事、回合完成标记与快照。
5. 提交后推送。提交成功但客户端没收到，应按事件序号补发，不能重新运行整个回合。
6. 重启扫描未完成回合：未规划则重新规划；已有计划/骰点则从叙事继续；已提交则只补发。离线队伍的长期任务可进入 `paused`，下次加入恢复。

提供的是**游戏效果恰好一次应用**，不是承诺模型请求或计费恰好一次。响应在途中丢失时，上游可能已经计费；可以重试叙事，但已保存骰点与结算不得改变。未保存的叙事文本在重试后可能不同。

`delta` 流式片段如需显示，必须标记为草稿并携带 attempt_id，不能当作存档承诺。首版建议规划和结算使用非流式结果，完成后广播完整回合；先保证稳定，再优化流式体验。

### 用户侧恢复体验

- 我的冒险：显示战役名、队友、最近保存时间、当前章节、“继续”。
- 重新加入：下发有权限的状态快照、最近日志、待处理检定和本轮已提交行动。
- 处理中断：显示“检定结果已保存，正在恢复主持叙事”；允许对同一请求重试，不提供重新掷骰按钮。
- 暂停：房主停止接收新回合，当前回合完成或安全停留于持久化阶段后暂停；离线不清空角色。
- 回滚若以后开放，创建新的分支/恢复版本并保留审计信息，不能与失败重试共用一个“重来”实现。

## 7. 多人协议与界面

首版目标为 4–6 人邀请制小队，也允许一名测试者控制多个预设角色。房主负责开团、暂停和管理席位，AI 担任 DM；房主默认不因此获得模组隐藏情报。

探索阶段收集每名活跃角色的一项行动，再批量裁决；玩家明确选择暂离才从等待集合中排除，短时断线不能悄悄替其决策。房主强制推进时记录哪些角色本轮未行动。战斗则严格依照先攻和轮到的角色接收动作。

建议消息：

```json
{
  "type": "trpg_action",
  "campaign_id": "uuid",
  "character_id": "uuid",
  "client_action_id": "uuid",
  "expected_revision": 12,
  "action": {"kind": "describe", "text": "我检查门上的机关"}
}
```

其他请求：`trpg_campaign_list/create/join/resume`、`trpg_ready`、`trpg_pause`、`trpg_recap`；响应：`trpg_ack`、`trpg_view`、`trpg_event`、`trpg_error`。`resume` 携带 `after_seq`，服务端在同一读快照中确定当前 revision 与事件高水位，然后补发；缺口过大时重新发送完整视图。

服务器从会话确定 actor_user_id，不能相信客户端传来的用户身份。检定结果、DC、伤害、HP 和金币不是客户端可写字段。查看摘要和桌外问答不推进时间；桌外模型只能读取公开或角色可见的内容。

桌面布局：中央故事日志与输入；一侧角色卡/资源，另一侧任务、已知线索、队伍状态；移动端使用标签页。支持自然语言并提供 2–4 个可选建议，按钮不限制玩家自由描述。地图和完整角色编辑器在核心循环稳定后加入。

日志用 textContent 或经过可靠净化的 Markdown 渲染。所有视图和事件均先在服务端按权限投影；不能把 DM 密档放在浏览器再用 CSS 隐藏。原始提示词、工具消息和后台秘密永不作为通用房间广播。

## 8. 场景包与规则覆盖

建议内容包至少包含：

```text
manifest.json          # id、版本、规则版本、来源hash、人数、等级、素材许可信息
public.json            # 封面文案、无剧透简介、玩家可选背景
scenes.json            # 地点、出口、朗读内容引用、进入条件
clues.json             # 发现条件、可见范围、替代获取途径
npcs.json              # 动机、知识边界、资料卡引用
encounters.json        # 战斗阵容、触发、逃跑/投降条件
timeline.json          # 游戏时间阈值、一次性事件、玩家介入后的取消条件
endings.json           # 完成条件、奖励、后续关系
source-index.json      # 每条数据对应PDF页码和人工校验记录
```

这里是待实现契约，不代表已经抽取完成。导入流程为：本地按页抽取 → 去除页眉页脚 → 人工检查双栏阅读顺序和地图 → 生成条目草稿 → 校验引用/冲突/缺失资料 → 人工确认 → 固定版本。PDF 内容只作为资料，里面的文字不能当作系统操作指令执行。

优先采用这些 PDF 对应的传统 5e 入门规则范围，具体版本以内容包声明固定；不要自动混入 2024 修订规则。最低可玩实现：

- 六项属性、技能/熟练、属性检定/豁免、优势劣势、被动察觉。
- 先攻、行动/附赠动作/反应、移动与触及、AC 与命中、伤害/抗性、治疗、0 HP 和死亡豁免。
- 近战击倒、俘虏、休息、有限的预设职业能力与法术，装备和背包。
- 检定成功不总需要掷骰；不能把自然 20/1 的攻击规则套到所有技能检定。
- 剧本相关的追踪、时间推进、岗哨警报、NPC 逃跑和任务条件。

预设角色和可选法术按已实现能力白名单生成；每个例外必须明确标注。若选用区域距离替代方格，则称为“5e 简化模式”，不能宣称完整 5e 规则实现。基础战斗不是只完成一个 d20 比较就算完成。

## 10. 实施顺序与验收

| 阶段 | 交付 | 完成判据 |
| --- | --- | --- |
| A：持续战役骨架 | 表迁移、权限、命令/事件/快照、大厅入口、预设角色、mock DM | 多账号加入；刷新和服务重启后恢复；重复/越权请求被拒绝；不影响牌桌与庄园 |
| B：真实 AI 回合 | 异步官方 API、计划校验、d20、叙事、调用预算与错误恢复 | 真实 Key 下完整跑通；超时后不重掷不重复结算；记录延迟、usage 与失败率 |
| C：首个完整剧本 | 《追捕克仑可》私有场景包、依赖补齐、时间线、分支和必要战斗 | 从委托到任一结局可玩；调查失败仍有合理替代路径；暂停不推进世界时间 |
| D：体验与扩展 | 多人准备/暂离、移动端、摘要、导出备份；第二部冒险 | 长团恢复、可见性和内容质量验收后再开放更多用户 |

必要故障测试应覆盖：模型超时、429/5xx、非法工具参数、生成半途掉线、应用重启、提交后推送失败、两人同时推进、客户端双击、旧 revision、跨战役伪造角色、私密线索泄漏、保存版本迁移。对恢复逻辑用真实临时 SQLite 和进程重启，不只 mock 数据库。

剧本验收用一组固定行动路径：接任务 → 发现线索 → 潜入失败 → 战斗/谈判 → 活捉或逃脱 → 移交/其他结局。每条路径在检定前、掷骰后、叙事前、事务提交后各中断一次，恢复结果中的事实状态必须一致。模型文字不要求逐字一致。

真实模型评测建议对常规交涉、检定失败、规则争议、长对话回忆和越权指令各准备样例，记录首包/整轮延迟、token 消耗、JSON/工具合规率、事实矛盾率与剧透情况，再决定默认思考档位、上下文预算和是否增加向量检索。

接下来的默认开发切片是 **A 阶段 + 一段原创机关场景**，随后接真实 API，最后导入整部冒险。当前需要后续补充的只有第二个剧本、正式开放时的内容使用范围，以及实际联调时由部署者配置的 API Key；这些不妨碍先完成骨架。
